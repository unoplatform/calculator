# Decision: target Uno 7, not Uno 6.8

**Date:** 2026-08-30
**Status:** Accepted
**Supersedes:** the Uno.Sdk 6.7.18 / `net10.0-*` target stated in
[`../superpowers/specs/2026-08-30-two-root-refork.md`](../superpowers/specs/2026-08-30-two-root-refork.md)
and the Act 0 plan.

## Decision

The Uno Calculator becomes an **Uno 7 showcase**. Build against
`Uno.Sdk.Private` **7.0.0-dev.579** from the `uno-features` feed, targeting
**`net11.0-*`**.

## Why

1. **BC26 removes a blocker we had already hit.** Uno 7 makes `DependencyObject` a
   class rather than an interface, deleting the `DependencyObjectGenerator`
   (commit `c371084bb`, −792 lines). On Uno 6 every non-partial `DependencyObject`
   subclass upstream ships is a CS0260; on Uno 7 it just compiles. **Verified: CS0260
   count is 0** with the `partial` rewrite rule disabled. The spec's proposed fifth
   rewrite rule is retired before it was ever written.

   BC26's own rationale matches ours exactly: *"WinUI parity. Code written against
   WinUI semantics (where `DependencyObject` is a class) breaks less, not more."*
   That is the whole thesis of the two-root strategy, so Uno 7 is strictly better
   aligned with it than Uno 6.

2. **Skia everywhere is now the platform default, not a choice we impose.** Uno 7
   drops the native mobile targets, which is exactly requirement #3. The flip side:
   the `-renderer native` escape hatch assumed by spike S4's mitigation **no longer
   exists**, so accessibility on Skia becomes a hard dependency rather than a
   preference. S4 rises in priority accordingly.

3. **It is a showcase.** The app is meant to demonstrate Uno 7, so shipping it on 6.8
   would defeat the purpose.

## Consequences

- **`.NET 11 SDK required.** Installed locally per `dotnet:setup-local-sdk` into a
  gitignored `.dotnet/` with `global.json` `paths: [".dotnet", "$host$"]`, so no
  system install is touched and CI can reproduce it with one script.
- **A prerelease private feed is now a build dependency.** `nuget.config` must carry
  `uno-features`, and CI needs credentials for it. Pin an exact version; a floating
  `7.0.0-dev.*` would make builds irreproducible.
- **The version is a moving target.** dev.579 today. Bump deliberately, never
  automatically, and record the bump.
- Spec and Act 0 plan TFM/SDK references are superseded by this document. The
  strategy — two roots, disjoint paths, glob-the-whole-project ingest — is unchanged.

## Evidence

First full-glob ingest against Uno 7 — all 102 upstream `.cs` and 26 `.xaml`
rewritten and linked, `partial` injection **off**:

| | Uno 6.6.14 / net10 | **Uno 7.0.0-dev.579 / net11** |
|---|---|---|
| CS0260 (non-partial `DependencyObject`) | present, blocking | **0** |
| Errors in ingested code | not separable | **186, from 3 causes** |

The 186:

| Cause | Count | Fix | Already in spec? |
|---|---|---|---|
| CS0246 — `CalcManager.Interop` types (`ExpressionCommandWrapper` ×46, `CalcManager` ×34, `CalculatorManagerWrapper`, `HistoryToken`, `UnitWrapper`, `CategoryWrapper`, …) | ~136 | build the managed interop seam | **Yes** — Act 2 P5 |
| CS0246 — `GraphControl` types (`GraphControl` ×38, `EquationLineStyle` ×6) | ~38 | the types-and-enums shim | **Yes** — already specced |
| CS0579 — upstream `Properties/AssemblyInfo.cs` duplicates SDK-generated attributes | 10 | exclude from ingest, or `GenerateAssemblyInfo=false` | No — new, trivial |
| CS0104 — `WindowActivatedEventArgs` ambiguous between `Windows.UI.Core` and `Microsoft.UI.Xaml` (`TitleBar.xaml.cs:190`) | 2 | one `using` alias | No — new, trivial |

Every remaining error is explained, and two of the three causes are components the
spec already planned to build. Nothing unexpected surfaced.

### After fixing the two trivial causes

Both were applied and verified: an ingest exclusion for `**/Properties/AssemblyInfo.cs`,
and one fork-owned `global using WindowActivatedEventArgs = Microsoft.UI.Xaml.WindowActivatedEventArgs;`.
Neither touches an upstream file, so the zero-edit invariant holds.

Result: **186 → 174 errors, all CS0246.** The entire remaining gap between "all 102
upstream files ingested" and "compiles" is now **13 distinct types**, across exactly the
two shims already in the spec:

| Shim | Types needed |
|---|---|
| `CalcManager.Interop` (managed seam, Act 2 P5) | `CalcManager` (ns), `CalculatorManagerWrapper`, `CalculatorMode`, `CommandType`, `ExpressionCommandWrapper`, `HistoryToken`, `UnitWrapper`, `CategoryWrapper`, `UnitConversionEntry`, `ConverterDataLoaderBase` |
| `GraphControl.Shim` (types-and-enums only) | `GraphControl`, `EquationLineStyle`, `GraphViewChangedReason` |

This is the P5 acceptance surface, enumerated rather than estimated: implement these 13
and the ingested upstream app compiles. It is also a far tighter target than the spec's
"~42 methods" framing implied, because the compiler — not a human reading `.idl` — produced
the list.

A further ~1150 diagnostics appear **inside Uno's own generated XAML output**
(CS0122, CS9348, CS0538, CS1527). These are cascade from the unresolved types above,
not defects in the rewritten sources, and are expected to clear once the interop and
graphing shims exist. They are explicitly **not** counted as work.
